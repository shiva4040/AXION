## 1. Overview & ADR Governance

Architecture Decision Records (ADRs) capture critical technical, architectural, and research methodology choices made during the development of AXION. Every ADR documents:
- **Decision ID & Title**
- **Context & Problem Statement**
- **Options Considered** (with pros and cons)
- **Selected Option & Justification**
- **Trade-offs & Consequences**
- **Status** (`FINAL` or `PROVISIONAL`)

### ADR-001: Unified PostgreSQL 16 + pgvector Storage vs. Separate Dedicated Engines

- **Status:** `FINAL`
- **Context:** AXION requires relational persistence (users, projects, documents, provenance), vector embeddings (for semantic search), and graph adjacency representations (for concepts and cross-domain links).
- **Options Considered:**
  1. *Option A (Polyglot Persistence):* PostgreSQL for relational data + Pinecone/Qdrant for vector embeddings + Neo4j for the knowledge graph.
  2. *Option B (Unified Relational + Extension):* PostgreSQL 16 with `pgvector` for embeddings and indexed relational adjacency tables for graph nodes/edges.
- **Decision:** **Option B (PostgreSQL 16 + pgvector)**.
- **Justification:**
  - *ACID Consistency:* Allows transactional joins between document chunks, bounding-box coordinates, vector embeddings, and knowledge graph edges in a single database transaction.
  - *Operational Simplicity:* Eliminates the distributed synchronization, failure modes, network latency, and maintenance burden of three separate database daemons during early and intermediate phases.
  - *Cost & Portability:* Runs locally in a single Docker container; no proprietary cloud vector SaaS dependencies.
- **Consequences & Trade-offs:**
  - Extremely large graphs ($> 10^7$ edges) may experience slower multi-hop traversal in relational SQL compared to native graph index-free adjacency.
  - *Mitigation:* Multi-hop queries are bounded by $k$-hop neighborhoods, recursive CTEs are indexed on `(source_node_id, relation_type)`, and active subgraphs are loaded into NetworkX in memory for algorithmic analysis. Neo4j migration remains an option for Phase 5 if scale requires it.

### ADR-002: Isolated Container Sandbox vs. In-Process Python Execution

- **Status:** `FINAL`
- **Context:** Components 4 and 8 must execute mathematical calculations, statistical tests, and physical simulations dynamically generated by the system or submitted by users.
- **Options Considered:**
  1. *Option A (In-Process Python `exec` / `eval` with AST whitelist):* Parsing and executing Python code within the host application process using restricted AST nodes.
  2. *Option B (Isolated Ephemeral Docker Container):* Spawning an isolated Docker container with dropped capabilities, read-only root filesystem, memory/CPU quotas, and disabled networking.
  3. *Option C (Wasm / Pyodide in Node/Browser):* Running Python compiled to WebAssembly.
- **Decision:** **Option B (Isolated Docker Container)** with Option A restricted to symbolic SymPy parsing in Component 4.
- **Justification:**
  - Python AST whitelisting is historically insecure; attackers and malformed code frequently bypass restricted globals via object traversal (`__subclasses__`).
  - Scientific Python packages (NumPy, SciPy, Pandas) require compiled C/Fortran extensions that cannot be safely sandboxed in-process.
  - Docker provides kernel-level namespaces, cgroups for memory/CPU capping, and `--network none` to guarantee zero data exfiltration.
- **Consequences & Trade-offs:**
  - Container spin-up introduces 200–500 ms latency per run.
  - *Mitigation:* Pre-warmed container worker pools and warm standby containers eliminate initialization lag.

### ADR-003: Model-Agnostic LLM Provider Abstraction

- **Status:** `FINAL`
- **Context:** AXION uses foundation LLMs for text extraction, candidate conceptual linking, and query decomposition. Tying the architecture to a single proprietary vendor (e.g., OpenAI or Google) creates vendor lock-in and risks breaking benchmark reproducibility.
- **Options Considered:**
  1. *Option A (Direct Vendor SDK):* Hardcoding calls to `openai` or `google-generativeai`.
  2. *Option B (LangChain / LlamaIndex):* Relying entirely on monolithic third-party orchestration frameworks.
  3. *Option C (Lightweight Internal Provider Interface):* A clean abstract base class (`LLMProvider`) implementing `generate_text` and `generate_embeddings`, with concrete adapters for OpenAI, Anthropic, Gemini, and local vLLM.
- **Decision:** **Option C (Lightweight Internal Provider Interface)**.
- **Justification:**
  - Provides complete control over prompt formatting, temperature zeroing, token tracking, and structured Pydantic decoding without framework bloat or frequent breaking changes from rapid external library churn.
  - Enables flawless switching between commercial frontier models and self-hosted open-weights models (e.g., Llama 3, Mistral) for offline scientific reproducibility.
- **Consequences & Trade-offs:**
  - Requires maintaining our own adapter classes for each provider (~100 lines of code per adapter).

### ADR-004: In-Memory NetworkX Graph Operations + Relational Adjacency Storage

- **Status:** `PROVISIONAL` (Re-evaluated at Phase 3 completion)
- **Context:** Knowledge Graph traversal, structural analogy mapping (Weisfeiler-Lehman kernels), and community clustering require graph algorithmic execution.
- **Options Considered:**
  1. *Option A (NetworkX In-Memory):* Load domain subgraphs from PostgreSQL relational tables into in-memory `networkx.DiGraph` instances on demand.
  2. *Option B (Native Graph Database - Neo4j):* Maintain a live Neo4j instance using Cypher queries.
- **Decision:** **Option A (In-Memory NetworkX + PostgreSQL Relational Adjacency)**.
- **Justification:**
  - NetworkX provides the most extensive collection of scientific graph algorithms, isomorphism solvers, and centrality metrics in Python.
  - For investigation-level subgraphs ($10^2$ to $10^4$ nodes), loading from PostgreSQL into RAM takes under 15 ms and provides orders-of-magnitude faster algorithm execution than remote Cypher calls over bolt sockets.
- **Consequences & Trade-offs:**
  - Does not support graphs with $> 10^6$ active nodes residing simultaneously in memory.
  - *Re-evaluation Condition:* If global cross-domain graph traversal across $> 100,000$ active nodes causes memory pressure or exceeds 500 ms latency, ADR-004 will be amended to introduce a dedicated Neo4j or Memgraph instance.

### ADR-005: Synthetic Scientific Universes for Research Anti-Contamination

- **Status:** `FINAL`
- **Context:** Frontier LLMs have already ingested published scientific papers during pretraining. Evaluating AXION on published scientific literature cannot determine whether a model solved a problem through reasoning or through memorization.
- **Options Considered:**
  1. *Option A (Only Real-World Literature):* Use real ArXiv papers published in the last 30 days.
  2. *Option B (Synthetic Counterfactual Universes):* Construct self-consistent synthetic domains with novel, fictional physical laws and constants, alongside real-world engineering tasks.
- **Decision:** **Option B (Synthetic Universes + Real-World Suite)**.
- **Justification:**
  - Guarantees absolute zero pretraining contamination. If an LLM answers a multi-hop question about *Zephyrian Phonon Transport*, it can only have done so by extracting and reasoning over the provided synthetic documents.
  - Enables exact, mathematical ground-truth verification of multi-hop paths and transfer decisions.
- **Consequences & Trade-offs:**
  - Requires manual or semi-automated formal authoring of synthetic laws, equations, and invariant sets.

### ADR-006: Strict 4-Stage Cognitive Pipeline vs. End-to-End LLM Prompting

- **Status:** `FINAL`
- **Context:** Conventional systems feed retrieved chunks directly into an LLM prompt and expect it to solve cross-domain problems in a single turn.
- **Options Considered:**
  1. *Option A (Prompt Stuffing):* `Prompt(Chunks + Query) -> Answer`.
  2. *Option B (Strict 4-Stage Neuro-Symbolic Pipeline):* `Retrieval -> Composition -> Transfer -> Validation`.
- **Decision:** **Option B (Strict 4-Stage Pipeline)**.
- **Justification:**
  - Decouples retrieval from synthesis, synthesis from analogical transfer, and transfer from empirical verification.
  - Allows isolating failure modes: did the system fail because it retrieved the wrong chunk, because the units were incompatible, because the analogy was invalid, or because the numerical calculation failed?
- **Consequences & Trade-offs:**
  - Higher orchestration complexity; requires state machine management across reasoning steps.

### ADR-007: Structural Isomorphism (WL Subtree Kernel) for Cross-Domain Transfer

- **Status:** `PROVISIONAL` (Phase 3 Validation)
- **Context:** Component 6 must discover structural analogies between disparate scientific domains without relying on lexical keyword overlap.
- **Options Considered:**
  1. *Option A (Embedding Cosine Similarity on Node Names):* Fails because "electric potential" and "hydraulic pressure" have low cosine similarity.
  2. *Option B (Weisfeiler-Lehman Graph Kernels + Relational Signature Matching):* Compares graph topological structures and relation patterns ($u \xrightarrow{governed\_by} v$).
  3. *Option C (Pure LLM Few-Shot Analogy Prompting):* Prompts an LLM to "find an analogy".
- **Decision:** **Option B (Hybrid: WL Graph Kernel + LLM Hypothesis Extraction)**.
- **Justification:**
  - Topological graph kernels identify structural equivalence based on connectivity and causal directionality rather than surface words.
  - The LLM is used to hypothesize semantic mappings, but the graph topology and Applicability Guard verify structural and physical validity.
- **Consequences & Trade-offs:**
  - Graph isomorphism algorithms can be computationally expensive on large dense graphs. Must be restricted to bounded ego-subgraphs ($k \le 3$).

### ADR-008: Bounding-Box Coordinate Provenance Ingestion (PyMuPDF)

- **Status:** `FINAL`
- **Context:** Citations must be verifiable down to visual bounding boxes on original document pages.
- **Options Considered:**
  1. *Option A (Plain PyPDF / pdfminer):* Slow, poor coordinate extraction, drops table structures.
  2. *Option B (PyMuPDF / fitz):* Ultra-fast C-based engine, precise bounding box extraction for text, vector drawings, tables, and images.
  3. *Option C (OCR / LayoutLM):* Heavyweight, requires GPU inference for basic PDFs.
- **Decision:** **Option B (PyMuPDF)**.
- **Justification:**
  - Processes a 20-page scientific paper in under 1.5 seconds.
  - Captures exact $(x_0, y_0, x_1, y_1)$ coordinates for every text span, enabling the frontend PDF viewer to visually highlight citations.
- **Consequences & Trade-offs:**
  - Cannot extract text from scanned bitmap PDFs without an OCR extension (Tesseract). OCR support will be added as a fallback plugin if needed.

### ADR-009: Epistemic Ladder (Tiers 1–4) Schema Enforcement

- **Status:** `FINAL`
- **Context:** To eliminate hallucination and false authority, AXION must prevent generated inferences or speculative hypotheses from being stored or presented as primary facts.
- **Options Considered:**
  1. *Option A (Freeform Text with Disclaimers):* Text outputs include generic warnings ("AI may make mistakes").
  2. *Option B (Strict Database Enum & Pydantic Schema):* Every node, edge, and statement must carry one of four explicit epistemic tiers (`FACT_DOCUMENTED`, `INFERENCE_DEDUCED`, `HYPOTHESIS_CONJECTURED`, `FINDING_VALIDATED`).
- **Decision:** **Option B (Strict Database Enum)**.
- **Justification:**
  - Enforces scientific rigor at the database and API level. Downstream reasoning components can filter queries by confidence tier (e.g., "only use Tier 1 facts and Tier 4 validated findings for critical engineering sizing").
- **Consequences & Trade-offs:**
  - Extra metadata overhead for every statement.

### ADR-010: Asynchronous FastAPI + SQLAlchemy 2.0 Backend Core

- **Status:** `FINAL`
- **Context:** The backend must handle concurrent long-running tasks (document ingestion, graph queries, LLM API calls, Docker sandbox runs) without blocking HTTP threads.
- **Options Considered:**
  1. *Option A (Flask / Django Synchronous):* Blocks worker threads during external API and sandbox calls.
  2. *Option B (FastAPI with asyncio + SQLAlchemy 2.0 asyncpg):* Native Python async/await, non-blocking I/O, automatic OpenAPI documentation, and strict Pydantic v2 data validation.
- **Decision:** **Option B (FastAPI + SQLAlchemy 2.0 asyncpg)**.
- **Justification:**
  - Handles high-concurrency async I/O efficiently.
  - Seamlessly integrates with modern Python typing and WebSocket connections for streaming reasoning logs to the frontend.
- **Consequences & Trade-offs:**
  - Requires developers to maintain async discipline (avoiding blocking CPU calls in event loops). Long computations are offloaded to background worker threads or Docker containers.
